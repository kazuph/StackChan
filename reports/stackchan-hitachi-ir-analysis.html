StackChan / HITACHI AC / IR

なぜ「スニッフした波形をそのまま送る」だけでは勝てなかったのか

結論: 受信波形は HITACHI_AC424 らしい先頭形状を持っていたが、キャプチャ終端の欠落・ジッタ・ノイズ混入・状態フレーム生成の不足・送信光量不足が重なった。解析済みライブラリの状態生成を使うと論理層は通り、最後に残ったのは物理層のIR出力だった。

今回の最短結論

370 / 424

スニッフ波形の復号可能ビット相当

有効キャプチャの leader/header は近いが、後半まで見ると 424bit 完走に足りない捕捉があった。

424 / 424

生成波形のビット数

ESPHome / IRremoteESP8266 の HITACHI_AC424 相当の状態生成で、53 bytes = 424 bits を安定生成。

近距離必須

最後に残った制約

StackChan内蔵IR送信はGPIO5の単発送信LED。家電リモコン級の光量・指向性ではない。

なぜスニッフ再送だけではだめだったか

HITACHIエアコンは「ボタンコード」ではなく「状態フレーム」

テレビのNECコードのような短いコマンドではなく、電源、温度、運転モード、風量、各byteの反転ペアを含む長い状態を送る。だから、1箇所でも欠けると「ONっぽい何か」ではなく「壊れた状態フレーム」になる。

受信rawは「復号の材料」であって完成品ではない

今回の受信ログは leader/header から HITACHI_AC424 らしさは見える。ただし、受信モジュールの出力はキャリアを消した後のエッジ列であり、ジッタ、末尾欠落、短いノイズ捕捉が混じる。そのまま再送するより、プロトコルとして復号してから再生成する方が強い。

ライブラリが勝った理由

使用した知見は IRremoteESP8266 / ESPHome の HITACHI_AC424 相当。実装では swiftbar/stackchan_action.py に 53 bytes のベース状態、温度・モード・風量・電源byte、反転byte再計算、LSB-first raw生成を移植した。

最後は光量の問題

生成rawで動いたのに近距離必須だったので、論理層は通っている。残りは送信LEDの光量、指向性、駆動電流、配置。メーカー純正リモコンが大きいIR LEDや複数LED、専用ドライバを持つ理由がここ。

StackChan IRハードウェア情報

送信ピン GPIO5 / IR_SEND。公式PinMapでも G5 が IR_SEND。今回のfirmware実装も IR_SEND_GPIO GPIO_NUM_5。
受信ピン GPIO10 / IR_REC。公式PinMapでも G10 が IR_REC。
受信部品 IRM56384。公式仕様とTouch基板回路図に記載あり。38kHz系の赤外線リモコン受信モジュール。
送信LED型番 公開資料上は個別型番未記載。 公式仕様は「infrared transmitter」とだけ記載。公開回路図テキスト抽出でも送信LEDの具体型番・順方向電流・放射強度は確認できなかった。
今回の送信設定 ESP-IDF RMT、38kHz carrier、duty 33%、active-high、raw duration最大1200要素。

実務上の判断: StackChan内蔵IRは「近距離なら家電制御できる」レベル。部屋全体へ飛ばすなら、外付けIRブラスター、トランジスタ/MOSFET駆動、複数LED、適切な照射角の設計が必要。
